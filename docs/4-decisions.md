# Decisions

| # | Date | Decision | Why | Rejected alternative |
|---|---|---|---|---|
| D-01 | 2026-10-06 | Use the design system **from source** through Vite aliases, not the published package | Library fixes show up immediately; no publish cycle while prototyping | Install the package from the registry: slow feedback, and needs tokens |
| D-02 | 2026-10-06 | Vue 2.7 Options API, plain JS in prototypes | It's the library's stack; its components won't run on Vue 3 | Vue 3 / `<script setup>` (from a generic rules template) |
| D-03 | 2026-10-06 | Load the library's `global.css` and rebind `body` to tokens | Match production styling while keeping dark mode working | Tokens only (diverges from production), or `global.css` as-is (breaks dark mode) |
| D-04 | 2026-10-06 | Keep the library's catch-all safelist (8 MB CSS) | Components build class names at runtime; trimming would silently drop styles | A sandbox-only safelist override |
| D-05 | 2026-10-06 | Always-on rules in CLAUDE.md, the workflow as a skill, Cursor rule as a pointer | One source of truth; the workflow loads only when needed | A single long `.cursorrules` copied per tool |
| D-06 | 2026-10-06 | Prototyping may fix or add to the library: fix in place, fork, or create a new component, always flagged (`PROTOTYPE-CHANGE`) and logged | Prototypes shouldn't be blocked by library gaps, and every change stays reviewable for an MR | Never touch the library (blocks work), or hand-build lookalikes (drift) |
| D-07 | 2026-10-06 | Verification uses puppeteer-core with the installed Edge | Exact viewports, full-page captures, real console capture, no browser download | Edge headless CLI (wrong viewport, F-010) |
| D-08 | 2026-10-06 | Responsive from 390px to 1440px+, verified at 1440, 1024 and 390 | Product requirement | Desktop-only |
| D-09 | 2026-10-06 | Hosting (Vercel or similar) deferred | A hosted build needs the library source at build time (monorepo, submodule or package) | — |
| D-10 | 2026-10-06 | Two case studies: internal (full detail) and public (anonymised) | Same work serves the team and external audiences | One document with redactions |
| D-11 | 2026-10-06 (refined 2026-10-07) | When Figma and live library defaults disagree, **code wins** and Figma is aligned to it, **unless the code contradicts its own component family or spec** (e.g. StatusChip lacking the label padding Chip has); then Figma stays and the code gets a change request in the library log | The components are live in production; Figma changes reach designs through the library update | Changing code (ripples through every table and page in production) |
| D-12 | 2026-10-06 | Components missing from code are added to the system on both sides (Figma variant + library code + Code Connect), not kept in prototypes | Reuse, and correct Dev Mode snippets | Prototype-local workarounds |
| D-13 | 2026-10-07 | **Preconstruction is one self-contained module**: tools Bidding, Prequalification, Directory, Configure, each with its own side-nav rail. Directory holds Companies (a subcontractor profile and its Qualification summary are pages inside it, not rail items); prequalification settings live under the module's Configure. Teal accent | Matches how Finance and Document end with Configure; new Figma variants only, no edits to the Project or Admin modules | Directory under the Project module's existing Directory tool and settings under Admin › Configuration (edits two existing modules) |
| D-14 | 2026-10-07 | **Figma is the source of truth.** When Figma and code disagree, code is changed to match Figma and logged (P-NNN); obvious Figma slips are kept as drawn and flagged for design | Stated by the user (first applied to Button, P-015). Supersedes the "code wins by default" rule in D-11. Earlier alignments of Figma to code (P-003 / P-004, P-012) were the user's explicit choices and stand | Code wins by default (D-11) |
| D-15 | 2026-10-08 | **Candidate stage for components missing on both sides.** Proposal doc (`docs/components/<Name>.md`) → built in `src/candidates/<Name>/` and used by a prototype → drawn in Figma with variables bound for a design iteration → promoted into the library with stories, README, `.figma.js` and a P-row → candidate deleted | D-12 covers "in Figma, not in code". The Prequalification module needs components that exist nowhere yet; putting them straight into the library skips the design iteration, and keeping them in a prototype makes them lookalikes with no path back into the system | Straight into `componentsV2` (no design pass); prototype-local widgets (no reuse); Figma first (blocks the prototype on design time) |
| D-16 | 2026-10-08 | **Prequalification status is five independent dimensions** (request workflow, qualification outcome, qualification lifecycle, check execution, document validation) with user-facing labels and a tone per value, implemented once in `src/modules/prequal/status.js` (`docs/prequal/status-model.md`) | The PRD's single 12-value enum can't express "approved, renewal under review"; one shared vocabulary keeps six screens consistent and makes a status component possible | The PRD's flat enum; per-screen status strings |
| D-17 | 2026-10-09 | **Visual hierarchy rules for module screens** (stated by the user on the subcontractor portal; references: Linear, Mercury, Airwallex on Mobbin): one container level per view, hairlines instead of boxes, colour only on the primary action and on states that ask for action, one signal per status (check *or* word *or* chip), label-only buttons unless the icon carries meaning the label doesn't, a fixed footer for step navigation | The first portal build nested cards three deep (FormV2 card › DocumentSlot card › tinted file row) and put a coloured dot, coloured text and a chip on every status; the user asked for a more minimal, intentional hierarchy. Written down so the next screens (wizard, review, record) start from it | Per-screen taste; keeping the library card defaults everywhere |
| D-18 | 2026-10-09 | **Create flows are full-page create screens, not modals**: module nav stays, Title Bar / Workflow (`Status=Create`: back arrow, title, ID chip) heads the page, the form fills the content area, step navigation sits in a fixed bottom panel. Alternatives worth comparing are kept as a second prototype slug (`<slug>-<variant>`) sharing state and components | Stated by the user for the New request wizard; it is the app's existing pattern (RFI create) and has library components behind it. A modal hides the page context the user came from but gains nothing for a 4-step, scrolling form | ModalV2 wizard (kept as version B, `prequal-wizard-modal`) |
| D-19 | 2026-10-09 | **Create-screen layout: centred form column with an aligned footer.** The stepper and form sit in a centred 48rem column (`mx-auto max-w-3xl`); the fixed bottom panel spans the content area and its buttons align to the same column. All UI and pattern decisions are consolidated in `docs/5-ui-patterns.md`, linked from `CLAUDE.md` and the `prd-to-prototype` skill | The left-aligned column left ~40% of a 1440 screen empty and made the full-width footer's buttons look misplaced; the RFI create screen it copied fills that space with a right panel, which this screen doesn't have. Consolidating the rules keeps them through context loss | Left-aligned column (RFI layout without its panel); left column + a live request-summary right panel (possible later as its own version); full-width form |
| D-20 | 2026-10-09 | **Wide-form column is 56rem (896px)**, `max-w-4xl`; 48rem stays for short single-column forms. Applies to the New request wizard; rule in `docs/5-ui-patterns.md` §2 | The user asked for 10–15% wider than 48rem. Guidance puts the standard form maximum near 720px but allows wider for forms with tabular data, which this one has (two-column fields, requirements list, checks table, summary). 56rem is the next step on the scale (+17%) and gives ~436px per field column | 48rem (felt narrow on 1440); an arbitrary 52rem (not on the scale, arbitrary values are disallowed); full width (fields and rows too long) |
