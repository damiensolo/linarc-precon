# Decisions

| # | Date | Decision | Why | Rejected alternative |
|---|---|---|---|---|
| D-01 | 2026-10-06 | Use the design system **from source** through Vite aliases, not the published package | Library fixes show up immediately; no publish cycle while prototyping | Install the package from the registry: slow feedback, and needs tokens |
| D-02 | 2026-10-06 | Vue 2.7 Options API, plain JS in prototypes | It's the library's stack; its components won't run on Vue 3 | Vue 3 / `<script setup>` (from a generic rules template) |
| D-03 | 2026-10-06 | Load the library's `global.css` and rebind `body` to tokens | Match production styling while keeping dark mode working | Tokens only (diverges from production), or `global.css` as-is (breaks dark mode) |
| D-04 | 2026-10-06 | Keep the library's catch-all safelist (8 MB CSS) | Components build class names at runtime; trimming would silently drop styles | A sandbox-only safelist override |
| D-05 | 2026-10-06 | Always-on rules in CLAUDE.md, the workflow as a skill, Cursor rule as a pointer | One source of truth; the workflow loads only when needed | A single long `.cursorrules` copied per tool |
| D-06 | 2026-10-06 | Prototyping may fix or add to the library: fix in place, fork, or create a new component, always flagged (`PROTOTYPE-CHANGE`) and logged | Prototypes shouldn't be blocked by library gaps, and every change stays reviewable for an MR | Never touch the library (blocks work), or hand-build lookalikes (drift) |
| D-07 | 2026-10-06 | Verification uses puppeteer-core with the installed Edge | Exact viewports, full-page captures, real console capture, no browser download | Edge headless CLI (wrong viewport, F-010) |
| D-08 | 2026-10-06 | Responsive from 390px to 1440px+, verified at 1440, 1024 and 390 | Product requirement | Desktop-only |
| D-09 | 2026-10-06 | Hosting (Vercel or similar) deferred | A hosted build needs the library source at build time (monorepo, submodule or package) | — |
| D-10 | 2026-10-06 | Two case studies: internal (full detail) and public (anonymised) | Same work serves the team and external audiences | One document with redactions |
| D-11 | 2026-10-06 (refined 2026-10-07) | When Figma and live library defaults disagree, **code wins** and Figma is aligned to it, **unless the code contradicts its own component family or spec** (e.g. StatusChip lacking the label padding Chip has); then Figma stays and the code gets a change request in the library log | The components are live in production; Figma changes reach designs through the library update | Changing code (ripples through every table and page in production) |
| D-12 | 2026-10-06 | Components missing from code are added to the system on both sides (Figma variant + library code + Code Connect), not kept in prototypes | Reuse, and correct Dev Mode snippets | Prototype-local workarounds |
| D-13 | 2026-10-07 | **Preconstruction is one self-contained module**: tools Bidding, Prequalification, Directory, Configure, each with its own side-nav rail. Directory holds Companies (a subcontractor profile and its Qualification summary are pages inside it, not rail items); prequalification settings live under the module's Configure. Teal accent | Matches how Finance and Document end with Configure; new Figma variants only, no edits to the Project or Admin modules | Directory under the Project module's existing Directory tool and settings under Admin › Configuration (edits two existing modules) |
| D-14 | 2026-10-07 | **Figma is the source of truth.** When Figma and code disagree, code is changed to match Figma and logged (P-NNN); obvious Figma slips are kept as drawn and flagged for design | Stated by the user (first applied to Button, P-015). Supersedes the "code wins by default" rule in D-11. Earlier alignments of Figma to code (P-003 / P-004, P-012) were the user's explicit choices and stand | Code wins by default (D-11) |
